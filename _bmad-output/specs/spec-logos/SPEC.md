# Logos — AI 名词知识图谱与演化平台

## Why

碎片时代的信息过载——搜一个名词，开十几个标签页，大脑过载却仍看不到全景。现有工具要么手动（Obsidian），要么企业级（Neo4j），要么只有 API 无探索界面（Diffbot）。

**没有产品能将自动构建 + 可视化探索 + 时间轴演化三合一地面向普通用户。** 知识图谱市场（CAGR 18–32%，2026 年 ~$1.9B）中，「高自动化 × 面向普通用户」的象限是空白。

Logos 是「知识侦探」——输入一个名词，五分钟内看到关系全景和演化脉络。面向记者、创作者、研究者、和每个曾因信息过载而沮丧的普通人。

## Capabilities

- id: CAP-1
  intent: 用户输入任意名词（人物、概念、技术、产品等），系统自动识别实体类型并返回图谱数据。支持中英双语输入。对未索引的名词，自动从公开数据源构建图谱并缓存。
  success: |
    - 输入已知名词后 2 秒内展示图谱数据
    - 输入"涌现"和"emergence"返回同一实体图谱（跨语言对齐时）
    - 首次搜索后再次搜索立即命中缓存（<500ms）
    - 输入 <2 字符时提示输入更多
    - 无精确匹配时展示语义近似结果
    - 冷启动构建 ≤ 15 秒（含数据采集 + 分析）

- id: CAP-2
  intent: 系统以力导向图展示名词关联网络。节点可拖拽、缩放、悬停弹摘要、点击展开详情。边粗细 / 颜色区分类联强度和关系类型（影响、隶属、创作、其他）。
  success: |
    - 200 节点以内 2 秒渲染完成
    - 默认展示 50 个主要关联节点，滚动 / 缩放时增量加载
    - 悬停弹出摘要卡片（名称、类型、置信度、一句话描述）
    - 强关联边比弱关联边更粗；关系类型通过颜色编码区分
    - 低置信度关系以虚线展示，悬停显示来源
    - 提供过滤器（关联类型、置信度、时间范围）

- id: CAP-3
  intent: 系统自动提取名词演化的 5–10 个关键里程碑，以可交互时间轴展示。用户拖动时间滑块时图谱动态联动，仅显示该时间范围内的节点和边。
  success: |
    - 默认展示 5–10 个关键里程碑
    - 支持年 / 十年 / 世纪缩放粒度
    - 时间轴-图谱联动延迟 < 500ms
    - 里程碑标题 ≤ 20 字，附简要说明和来源链接
    - 跨度 50 年以上的概念至少提取 5 个里程碑
    - 无历史数据时显示"该概念的演化数据有限"

- id: CAP-4
  intent: 系统识别搜索实体是否为人名。人物节点在搜索排名、图谱展示和关联推荐中优先级最高，展示人物关系网络（师承 / 合作 / 竞争 / 隶属 / 亲属等）。支持递归探索——点击关联人物图谱中心切换，可回溯。
  success: |
    - 搜索人物名时图谱中心自动展示该人物的关联网络
    - 人物节点交互层级高于非人物节点（首位展示、更详细信息）
    - 人物关系类型具体化（非笼统"关联"）
    - 上一级探索上下文保留在面包屑导航中
    - 支持回溯到之前浏览过的人物

- id: CAP-5
  intent: 所有实体、关系、事实标注置信度等级（高 / 中 / 低）并在 UI 中可视化区分。用户可悬停 / 点击任一条关系或事实，查看其来源信息。
  success: |
    - 高置信度（多源交叉验证）无特殊标记
    - 中置信度（单一权威来源）带 ⚠️ 标记
    - 低置信度（LLM 推理 / 单一非权威来源）带 ⚠️ 标记并以虚线 / 暗淡色展示
    - 每个事实 / 关系可追溯到至少一个来源（名称 + 链接）
    - 多源信息显示所有来源
    - 提供置信度说明入口，标注规则透明可查

## Constraints

1. **图数据库单一化 — MVP 仅用 Neo4j（含原生向量索引 SEARCH 子句），暂不引入独立 Milvus。** 排除了其他向量数据库（Qdrant、Pinecone）和双库运维方案。
2. **可视化 2D-only — MVP 图谱可视化限于 D3.js 力导向图和 vis-timeline，不引入 Three.js 3D。** 排除了 3D 渲染管线和 WebGL 优化路径。
3. **模块化单体架构 — 后端采用 FastAPI 单进程模块化单体（非微服务）。** 排除了服务拆分、独立部署和跨服务事务。
4. **无用户注册墙 — MVP 不设强制注册 / 登录，不存储用户搜索历史。** 排除了认证系统、用户管理、及一切基于用户身份的功能。
5. **人物节点数据模型必有独立 `:Person` Label — 不可退化为统一 `:Entity` 类型。** 排除了单一实体表标签策略。
6. **每条关系的数据模型必含 `source` / `confidence` / `evidence` 三个字段。** 排除了简化关系模型（仅存类型和方向）。
7. **API 传输层统一 snake_case — 前端内部变量用 camelCase，API 层不做字段名转换。** 排除了 camelCase API、单独转换中间件。
8. **LLM 成本控制嵌入架构 — 三层缓存（浏览器 → Redis → Neo4j）+ 分层检索（L1 优先）+ 模型选择策略。** 排除了单一模型调用策略。

## Non-goals

1. 用户注册 / 登录系统 — Phase 2
2. 个人知识库 — Phase 2
3. 多名词对比 — Phase 2
4. AI 对话问答 — Phase 2（LLM 仅用于数据管道：实体提取、搜索结构化、摘要生成）
5. 3D 可视化 — Phase 2
6. 未来推演模式 — Phase 2+
7. 用户上传自有数据 — Phase 2
8. 移动端原生 App — 仅响应式 Web
9. 企业级功能（批量导入、Cypher API、RBAC）— 长期
10. 利益关系分析 — Phase 3

## Success signal

- **核心假设验证：** 普通用户是否愿意用图谱化方式探索知识？7 日回访率 > 20%（领域研究经验基准）
- **性能：** 图谱加载 < 2s（200 节点以内）；图谱查询接口 P99 < 500ms（缓存命中）
- **质量：** 图谱实体准确率 > 90%（用户反馈采样 + 自动交叉验证）
- **技术健康：** 测试覆盖率 > 80%；服务可用性 > 99.5%

## Assumptions

- 7 日回访率 > 20% 作为核心假设验证的合理基准（领域研究的经验值，需实测校准）
- 知识图谱市场 CAGR 18–32% 的上升趋势在 MVP 验证期内不变
- Wikidata API 在 MVP 规模下服务可用性稳定
- LLM 在 MVP 中仅用于数据管道（实体提取、搜索结构化、摘要生成），运营成本可控
- 免费探索 + 高级付费（约 $9.99/月）的商业模式框架待验证，非 MVP 优先

## Open Questions

1. **~~AI 对话是否应在 MVP 出现？~~ ✅ 已决策：** AI 对话推迟至 Phase 2。MVP 中 LLM 仅用于数据管道（实体提取、搜索结构化、摘要生成）。架构文档的"AI 不可见原则"适用。
2. **冷门词质量基线？** 当公开数据仅有 3–5 条时图谱体验是否仍有价值？最低可接受标准是什么？
3. **用户对置信度的理解能力？** 普通用户是否能理解置信度标注系统，还是应该做得更隐式？
4. **首屏默认节点数？** 50 个是否太多 / 太少？
5. **合规细节：** 中国 AI 算法备案的具体流程、时限和材料要求需核实。
6. **核心假设第一验证方案？** 在技术实现启动前 / 同步，如何最小成本验证"用户愿意用图谱化方式探索知识"？
